# FEEDBACK_POLICY.md - 분석 피드백 정책

## 문서 목적

분석 결과를 사용자에게 제공하는 정책 — 실행 트리거, 사용자 데이터의 역할,
AI의 역할과 한계, 결과 보관, 사용자 반응과 운영자 품질 관리를 정의한다.

## 분석 실행 정책

- **모든 분석은 사용자 요청 시에만 실행한다.** 자동/주기적 분석은 없다.
- **단일 경기 분석**: 사용자가 경기 상세에서 분석을 요청하면 **즉시(동기)**
  처리한다. `analysis_jobs`를 생성하더라도 처리 자체는 동기 흐름으로
  완료하며, 사용자는 결과를 바로 받는다.
- **10경기/30경기 분석**: `analysis_jobs`에 작업을 적재하고 **비동기**로
  처리한다. 사용자는 작업 상태(대기/처리중/완료)를 조회하며, 완료 시 결과
  (`analysis_results`)를 확인한다.

## 사용자 데이터의 역할

- 사용자의 경기 데이터는 **랭커 기준 통계(`benchmark_stats`)와의 비교
  대상**이다.
- 사용자 데이터는 어떤 형태로도 모델 학습이나 `benchmark_stats`/
  `scoring_rule_sets` 생성에 입력되지 않는다(`DATA_MODEL.md` "사용자 데이터의
  위치" 참고).
- 분석 결과(`analysis_results`)는 해당 사용자에게 귀속되며, 다른 사용자의
  비교나 집계에 재사용되지 않는다.

## 표본 수와 신뢰도

- `docs/SPEC.md` 원칙("충분한 표본 수와 데이터 품질이 확보되기 전에는
  피드백을 제공하지 않는다")을 분석 결과 생성 시 적용한다.
- `benchmark_stats.sample_count`가 기준치 미달이면 해당 조건의 비교 항목은
  결과에서 제외하거나, "표본 부족으로 비교 불가"로 명시한다. 기준치 값은
  PENDING(`SCORING_RULES.md`).
- `CYPHER_ASCENT_B_MVP.md`의 "최근 1개 패치 우선, 부족 시 2개 패치 확장"
  규칙은 표본 부족 시의 1차 대응이다. 2개 패치로도 부족하면 해당 비교 항목은
  제공하지 않는다(추가 패치 확장은 이 MVP 범위 밖).

## AI 역할과 한계

`SCORING_RULES.md` "AI 역할 한정"을 정책으로 재확인한다:

- AI는 근거 설명, 우선순위 선정, 행동 지침 생성만 수행한다.
- AI는 통계/클러스터/percentile을 직접 만들지 않는다.
- AI 출력은 항상 사전에 계산된 `analysis_results.result_data`를 입력으로
  사용한다.

## 추측 금지 항목

`SCORING_RULES.md` "추측 금지 항목"(의도/사운드/시선/정보 획득 여부)을 피드백
문구 생성 시에도 동일하게 적용한다. AI 설명 생성 단계에서 이 항목들이 출력에
포함되지 않도록 하는 검증(예: 금지 표현 검토)은 구현 시점(TASK-034)에서
구체화한다.

## 결과 보관 정책

- `analysis_results`는 버전(`zone_definition_version`,
  `scoring_rule_version`)별로 **장기 보관**하며 삭제·덮어쓰기하지 않는다
  (`DATA_MODEL.md`).
- 사용자는 과거 분석 결과 이력을 조회할 수 있다(조회 UI는 Phase 5 Frontend
  Task 범위, 이 문서는 보관 정책만 정의).
- 데이터 삭제 요청(`docs/SPEC.md` 비기능 요구사항, GDPR 대응)이 있을 경우
  사용자 귀속 `analysis_results`/`feedback_reactions`도 삭제 대상에 포함한다.
  `ranker_roster`/`benchmark_stats`(랭커 집계 데이터)는 별도 동의 체계를
  따른다 — PENDING.

## 사용자 피드백 반응

- `feedback_reactions`(`DATA_MODEL.md`)를 통해 사용자는 분석 결과에 대해
  "도움됨 / 도움 안 됨 / 신고"로 반응할 수 있다.
- "신고"는 `analysis_qa_reviews`에 `flagged_by="user_report"`로 등록되며,
  운영자 검토 대상이 된다.

## 운영자 품질 관리

- `analysis_qa_reviews`(`DATA_MODEL.md`)를 통해 운영자가 분석 결과를
  검토한다.
- 검토 트리거: 사용자 신고("report" 반응) 또는 운영자가 직접 샘플링한 결과.
- 검토 상태: `"open"` → `"reviewing"` → `"resolved"`. 해결 방식(규칙 수정,
  결과 비공개 등)은 운영 프로세스로 별도 정의 — PENDING.
- 운영자 식별/권한 모델(누가 운영자인지, 별도 역할 체계 필요 여부)은 PENDING.

## 확정 사항 vs 검증 필요 사항

**확정**

- 모든 분석은 사용자 요청 기반
- 단일 경기 = 동기, 10/30경기 = 비동기(작업 큐)
- 사용자 데이터는 비교 대상, 학습 데이터 아님
- 결과는 버전별 장기 보관, 삭제/덮어쓰기 없음
- 사용자 반응(도움됨/도움 안 됨/신고) + 운영자 QA 구조 존재

**검증/정의 필요 (PENDING)**

- 표본 수 기준치(threshold) 값
- 랭커 집계 데이터(`ranker_roster`/`benchmark_stats`)의 동의/삭제 처리 방식
- 운영자 식별/권한 모델, QA 해결 프로세스 상세
- AI 출력의 "추측 금지 항목" 자동 검증 방법
